# UIコンセプト画像ワークフロー

## 目的

React実装前に、同一要件からPC・モバイルの視覚案を3方向生成し、好みだけでなく案件獲得に必要な情報伝達の強さで比較する。生成画像はコンセプト検討用であり、実績の証拠には使わない。

## 事前に固定する情報

- Heroの主語、見出し、説明、主要な導線
- Homeの10セクションと各セクションの目的
- 公開可能な経歴、制作物、証拠、リンク
- AxisがDevnetで実資金取引ではないという表示
- 使用可能な実在Axisスクリーンショットと出典
- PC 1440px、モバイル390pxで確認する代表viewport

未確認の数値や実績はプロンプトへ入れない。

## 生成する3方向

### A. Editorial Monochrome

大きなタイポグラフィと余白でポジショニングを最短で伝える。Axisは編集記事の特集のように展開し、情報密度を抑える。

### B. Flagship Case Study

Hero直後からAxisを強く見せ、課題・役割・実装・証拠の順で信頼を形成する。Devnet表記が埋もれない構造にする。

### C. Quiet Modular

落ち着いたモジュール構成で、実績・能力・プロセスを比較しやすくする。カードの乱用を避け、境界線と余白で階層を作る。

各方向でPCとモバイルを一組生成し、同じ文言・同じ証拠範囲を使う。Appleのアセットや画面を模倣せず、ネオン、ターミナル表現、過剰なグラデーション、装飾目的の3Dを除外する。

## 画像の扱い

- コンセプト画像: `public/images/concepts/<direction>/`
- 実在プロダクト画像: `public/images/product/axis/`
- 生成画像にAxisの架空UIを描かせない。必要な箇所はプレースホルダーとして明示する。
- 生成物には方向名、viewport、生成日、プロンプト版を対応するREADMEへ記録する。

## 比較基準

1. Full-Stack Engineerという主軸が最初の画面で伝わるか
2. タイポグラフィと情報階層が日本語で読みやすいか
3. 余白が上質さと理解速度の両方に寄与するか
4. Axisが強い証拠として見え、Devnetの注記も明瞭か
5. TypeScript / React / Next.jsが主軸で、Web3に偏りすぎないか
6. モバイルでも順序、行長、タップ領域が破綻しないか
7. モーションへ展開する理由と対象が説明できるか
8. アクセシビリティと実装コストに無理がないか

各項目を1〜5で採点し、コメントと重大な懸念を残す。採用案は一案に絞るが、他案の良い要素を混ぜる場合は混ぜる理由を記録する。

## 採用後

採用案から色、文字サイズ、行間、最大幅、余白、境界線、角丸をdesign tokenとして抽出する。モーションは目的、開始条件、duration、easing、interrupt、reduced-motion時の挙動を仕様化する。その仕様レビュー後にServer Componentを基本としてReact実装を始める。
